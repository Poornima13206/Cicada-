**Topic:** How to Answer Every Question and Win Maximum Marks (25/25) in Phase 2 Checkpoint

## 1. The 4 Concrete Evidences Judges Will Ask For

During the Phase 2 design checkpoint, the judges will request four specific pieces of evidence. Here is your exact script and reference:

### Evidence 1: Architecture diagram with the trust boundary and every network hop labeled
- **Where to show:** `docs/ARCHITECTURE.md` (Section 1).
- **Key Talking Point:**  
  *"We have divided the system into two distinct trust tiers. Tier 1 is 100% inside the customer's on-prem/VPC environment. All raw logs, secrets, and detailed traces remain strictly in Tier 1. Only allow-listed, scrubbed metadata crosses the network hop over TLS 1.3 to Tier 2 SaaS."*

### Evidence 2: The payload schema and the allow-list mechanism
- **Where to show:** `schemas/payload_schema.json` and `schemas/allowlist_config.json`.
- **Key Talking Point:**  
  *"We use a zero-trust schema approach (`additionalProperties: false`). Instead of merely trying to blacklist bad words, our allow-list validator drops any field that is not explicitly whitelisted. Furthermore, regex and Shannon entropy scrubbers redact passwords, bearer tokens, and private IPs."*

### Evidence 3: How the design behaves when SaaS is unreachable and how duplicates are avoided after reconnect
- **Where to show:** `docs/ARCHITECTURE.md` (Section 6) and `collector/collector.py`.
- **Key Talking Point:**  
  *"When SaaS drops, the collector automatically queues payloads into a persistent SQLite Write-Ahead Log (WAL) buffer. Every payload is minted with a unique UUIDv4. When connectivity restores, the SaaS deduplication cache checks incoming UUIDs against its database. If a payload was already received before the crash, it is acknowledged but ignored, guaranteeing 100% delivery, zero loss, and zero duplicates."*

### Evidence 4: Tenant isolation approach
- **Where to show:** `docs/ARCHITECTURE.md` (Section 7).
- **Key Talking Point:**  
  *"Every metadata record contains an immutable `tenant_id`. Ingest endpoints validate the collector's HMAC bearer token against the registered tenant. All database queries enforce tenant-scoped isolation (`WHERE tenant_id = ?`) with dedicated schema namespaces, ensuring complete tenant data separation."*

## 2. Answers to Specific Judge Questions (from Section 7)

### Q1: Exactly what data leaves the local environment, and what stays behind?
- **Answer:**  
  *"What stays behind: Raw application logs, user payloads, authentication records containing usernames/passwords, credentials, and internal IP addresses.*  
  *What leaves: Only aggregated numeric metrics (CPU, RAM, Latency, Loss), pseudonymized node hashes (`node-8f2a`), a local risk severity indicator (e.g., '5 failed logins detected locally'), UTC timestamp, and collector health status."*

### Q2: How does the collector decide which fields are allowed to be sent to SaaS?
- **Answer:**  
  *"The collector runs an explicit Allow-List Validator. Any incoming JSON object is sanitized against `schemas/payload_schema.json`. If an unknown field (like `user_password` or `stack_trace`) is present, the parser drops it completely before serializing the egress payload."*

### Q3: How do you prevent secrets or raw log content from being transmitted accidentally?
- **Answer:**  
  *"We employ a defense-in-depth pipeline:*  
  *1. High-entropy analyzer checks for random strings characteristic of API keys.*  
  *2. Regex scrubbers redact Bearer tokens, private RFC-1918 IPs, and credential patterns.*  
  *3. The schema validator drops any unwhitelisted key.*  
  *4. The Egress Proof Panel provides a live visual audit of every payload before transmission."*

### Q4: How do you distinguish a real anomaly from a normal usage spike?
- **Answer:**  
  *"Instead of relying on brittle static thresholds (e.g. alert if CPU > 80%), we calculate dynamic rolling baselines using Exponentially Weighted Moving Averages (EWMA) and rolling standard deviations. A spike during an expected 2 PM traffic surge is within normal variance; a sudden spike with high deviation (>3.0σ) that correlates with network packet loss is flagged as an anomaly."*

### Q5: How do you correlate multiple alerts into one incident?
- **Answer:**  
  *"We use graph-based temporal clustering. When multiple anomalies occur on the same node or connected services within a 30-second window, our correlation engine merges them into a single incident. This reduces alert noise and presents the operator with one actionable incident rather than 10 disconnected alerts."*

### Q6: Can you explain why the platform recommends a particular action?
- **Answer:**  
  *"Every incident generated by our AIOps engine includes an Explainability Drawer. It details: (1) which metrics triggered the alert, (2) the percentage contribution of each signal, (3) the reconstructed root-cause timeline, and (4) why this specific remediation was chosen based on our blast-radius impact score."*

### Q7: What safeguards are needed before automated remediation?
- **Answer:**  
  *"In our Autonomous Ops roadmap, we follow strict human-in-the-loop safeguards:*  
  *1. Policy bounds: Automated execution only runs on pre-approved, non-destructive actions.*  
  *2. Operator Approval: High-impact actions require explicit one-click operator confirmation.*  
  *3. Automated Rollback: Every action has an attached rollback script that executes if health does not improve within 60 seconds.*  
  *4. Immutable Audit Trail: Every simulation and execution is logged permanently."*

### Q8: How do you handle regions, tenant data residency, UTC time, and out-of-order events?
- **Answer:**  
  *"1. Regional Ingest: Collectors point to local regional gateways to minimize latency and obey local data sovereignty.*  
  *2. Data Residency: Tenant time-series partitions reside solely within the customer's selected region.*  
  *3. UTC & Timezones: All events carry standard ISO-8601 UTC timestamps, with local source timezone preserved for UI rendering.*  
  *4. Out-of-Order Handling: Storage indexes records by event generation time (`timestamp_utc`), not arrival time, so late-arriving records from an outage backlog slide accurately into history without distorting trends."*
